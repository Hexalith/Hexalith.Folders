# Folders resolution evidence: missing owner File source contract

The identity-only File authorization operation is **blocked**. Folders ships repository providers, but the inspected source exposes no durable owner File identity lookup or authoritative File lifecycle producer. Adding a handler, an unavailable source, or a mapping over path/blob identifiers would not deliver the prerequisite.

This is a new owner inspection under the [selected Projects decisions](../../../../_bmad-output/implementation-artifacts/6-4-prerequisite-decisions-2026-10-20.md) D2/D6 and [contract annex](../../../../_bmad-output/implementation-artifacts/6-4-resolution-evidence-contracts.md), especially section 4. Those documents and earlier inspection receipts retain their existing bytes. This report supplies source evidence, not qualification, deployment enrollment or prerequisite acceptance.

## Actual provider surface and identity namespaces

Both [GitHubProvider](../../src/Hexalith.Folders/Providers/GitHub/GitHubProvider.cs) with [OctokitGitHubApiClient](../../src/Hexalith.Folders/Providers/GitHub/OctokitGitHubApiClient.cs) and [ForgejoProvider](../../src/Hexalith.Folders/Providers/Forgejo/ForgejoProvider.cs) with [ForgejoSmartHttpGitTransport](../../src/Hexalith.Folders/Providers/Forgejo/ForgejoSmartHttpGitTransport.cs) are registered by [FoldersServiceCollectionExtensions](../../src/Hexalith.Folders/FoldersServiceCollectionExtensions.cs). [OrganizationProviderBinding](../../src/Hexalith.Folders/Aggregates/Organization/OrganizationProviderBinding.cs) selects `ProviderKind`; this source inspection does not establish which provider any deployment selects.

The actual [IGitProvider](../../src/Hexalith.Folders/Providers/Abstractions/IGitProvider.cs) surface provides capability discovery, repository creation/binding, `StageFileChangesAsync`, `CommitAsync` and `GetOperationStatusAsync`. It has no File identity registration/lookup, current parent/lifecycle read, mapping or File change/head API. `GetOperationStatusAsync` describes an operation, not current File existence.

The Projects [FoldersProjectFileReferenceDirectory](../../../../src/Hexalith.Projects.Server/Folders/FoldersProjectFileReferenceDirectory.cs) validates links through `GetFolderFileMetadataAsync(folderId, workspaceId, ...)` using a path. Its validation result carries no owner File identity. `RefreshFileReferenceAsync` explicitly returns Unavailable because no opaque reference lookup exists. Neither caller-supplied FolderId nor previous path validation establishes an identity mapping. The existing [consumer discovery](../../docs/contract/pd10-v2-consumer-discovery.md) also records that capability gap; its dated deployment claims are not current deployment evidence.

[ProjectAggregate.References](../../../../src/Hexalith.Projects/Aggregates/Project/ProjectAggregate.References.cs) checks FileReferenceId uniqueness only inside one Project's `FileReferences`; [ProjectStateApply](../../../../src/Hexalith.Projects/Aggregates/Project/ProjectStateApply.cs) removes the entry on unlink, so another link can reuse the same ID. The namespace is therefore at least Tenant/Project scoped, with link-instance/rebinding invalidation required. A permanent Tenant/FileReferenceId binding would conflate different Projects or later links. This is separate from the owner's File entity continuity.

There is also a missing mapping handoff: `ValidateLinkFileReferenceAsync` receives ProjectId, FolderId, workspace and path, but no FileReferenceId, and returns no owner identity or binding. The proposed annex File authorization query already requires an OwnerFileId. A real owner identity source alone would not connect these surfaces: owner-verified registration must bind the scoped reference/link instance to the verified File, and a content-free lookup must recover that binding for resolution under verified authority. No executable registration/lookup seam currently supplies that handoff.

## Lifecycle and authorization findings

`OctokitGitHubApiClient.StageFileChangesAsync` observes tree entries by path at an expected Git head and stages blobs. `ForgejoSmartHttpGitTransport.TryCreateTree` reads `parent.Tree[change.Path]`, validates mode/source SHA, then removes that path or creates a blob from replacement content. [ProviderFileChangeKind](../../src/Hexalith.Folders/Providers/Abstractions/ProviderFileChangeKind.cs) supports Add/Change/Remove only.

| Required case | Current source establishes | Still missing for resolution |
| --- | --- | --- |
| Same Tenant and exact parent | Folder authorization uses Tenant/Folder scope; mutation/version metadata includes scope | An authoritative owner File record binding its identity and lifecycle generation to its current Tenant and parent Folder. A Folder grant alone proves no File membership. |
| Active/existing File; absent or wrong parent | Folder read models distinguish missing/active/archived Folders | Current File existence/lifecycle read by owner identity, with identical denial for absent, denied, cross-Tenant and wrong-parent targets. |
| Permission/revocation | Strict Folder `read_metadata`, native Folder/Organization head checks and fail-closed outcomes exist | Resource-specific File metadata authority, complete native permission revision scope and a recheck before disclosure. |
| Rename/move | No explicit identity-preserving provider operation; remove/add has no continuity link | Owner-established continuity and atomic parent change/invalidation, including any out-of-band provider changes. No inferred rename by matching path/hash. |
| Content change/replacement | A staged path can receive another blob; index version inputs change | A rule and native generation/version evidence distinguishing the same File being edited from a different File replacing it. |
| Delete | Provider path removal and index-version tombstones | Authoritative File identity tombstone/invalidation and current-head evidence. |
| Delete/recreate; identical bytes at several paths | Blob identity can repeat; paths identify locations | Entity generation/identity rules preventing a removed File from validating its replacement or another path. |

[IWorkspaceFileContentStore.StageAsync](../../src/Hexalith.Folders/Aggregates/Folder/IWorkspaceFileContentStore.cs) returns only [WorkspaceFileContentStoreResult](../../src/Hexalith.Folders/Aggregates/Folder/WorkspaceFileContentStoreResult.cs) `Accepted`. [WorkspaceFileMutationAccepted](../../src/Hexalith.Folders/Aggregates/Folder/WorkspaceFileMutationAccepted.cs) carries mutation/workspace/path-digest/content-hash metadata, without a stable File identity or predecessor/successor lifecycle relation. [FolderState](../../src/Hexalith.Folders/Aggregates/Folder/FolderState.cs) contains no File catalog. A new mapping alone would therefore lack authoritative registration and update inputs. Index tombstones in [SemanticIndexingBridgeProjection](../../src/Hexalith.Folders/Projections/SemanticIndexing/SemanticIndexingBridgeProjection.cs) serve index egress; they do not supply current File lifecycle authority.

The default composition has further concrete execution gaps. `AddFoldersProviderReadiness` registers [UnconfiguredProviderOperationSourceResolver](../../src/Hexalith.Folders/Providers/Abstractions/UnconfiguredProviderOperationSourceResolver.cs) and [UnconfiguredProviderRepositoryTargetResolver](../../src/Hexalith.Folders/Providers/Abstractions/UnconfiguredProviderRepositoryTargetResolver.cs); the server registers [UnavailableWorkspaceFileContentStore](../../src/Hexalith.Folders/Aggregates/Folder/UnavailableWorkspaceFileContentStore.cs). Registered adapters and low-level staging code do not establish a configured authoritative mutation/lifecycle producer. Any deployment-specific replacement needs its own executable source evidence.

## Precise missing contract and resumption boundary

Folders needs a real executable owner source, backed by the selected provider or supported owner persistence, that supplies all of the following:

1. A canonical File identity namespace with documented validation/scope and durable entity continuity rules. Reuse an existing provider identity if a named executable API can substantiate those rules; no such API was found here.
2. An identity-addressed, content-free current read binding File identity to Tenant, exact parent Folder, existence/lifecycle generation, native resource revision and head/coverage evidence, with the actual observation instant. It must keep path, workspace, repository/provider address and content internal.
3. An authoritative registration/change/deletion producer maintaining that identity and parent across rename/move/edit/delete/replacement, including either coverage of out-of-band changes or an enforced boundary preventing them. Persisted mappings must use supported EventStore owner persistence and be recoverable; query execution cannot create or repair them.
4. Only the necessary Folders-owned mapping from the Tenant/Project/reference/link-instance namespace to canonical owner identity, populated through an owner-verified registration handoff and recovered through an authorized content-free lookup. Unlink/relink must invalidate or distinguish the old binding; File replacement must not resurrect it. These are missing capabilities, not a selected storage schema or a new reference-generation allocator. Existing references with no recoverable mapping need separately authorized owner-backed re-verification/relinking; no history rewrite, silent validation or conversion to NoMatch.
5. Strict current Tenant, parent, lifecycle and exact resource permission evaluation, including owner-side visibility/path-policy and sensitivity classification for the internally resolved target, followed by a stable native revision comparison before disclosure. The reused owner authority must demonstrate the annex's selected two-second resolution currentness boundary; `StrictRead()` success alone is insufficient. Absence, denial, cross-Tenant, policy-hidden and wrong-parent File targets share safe denial. Incomplete/stale/unavailable authority supplies no usable evidence. Cancellation propagates; metadata reads call no existing workspace/path/content or inspection-audit route.

These are required capabilities, not implemented API signatures. No `IFileProvider`, allocator, persistence schema, stub registration, backfill or mutation route is introduced by this report. A missing executable source is a dependency, not an unanswered design choice.

## Native Folder evidence and compatibility

The existing [FolderOwnerReadQueryHandler](../../src/Hexalith.Folders.Server/Queries/FolderOwnerReadQueryHandler.cs) verifies SDK `VerifiedQueryCaller`, exact query object and `delegated-owner-query`, then applies `read_metadata` with `StrictRead()`. Its [FolderOwnerReadResult](../../src/Hexalith.Folders.Contracts/FolderOwnerReadResult.cs) has only the positional Outcome. The handler performs one authorization pass, checks empty-object payload, matching EntityId/AggregateId and no paging, and calls no inspection audit.

Native fields are useful but currently insufficient for the annex receipt:

- [EventStoreFolderEffectivePermissionsReadModel](../../src/Hexalith.Folders/Authorization/EventStoreFolderEffectivePermissionsReadModel.cs) compares Folder `LastSequence` to its stream head and observes lifecycle. Its merged snapshot replaces Organization baseline row sequences with zero and retains the Folder watermark. The independent Organization revision is lost.
- [TenantAccessAuthorizer](../../src/Hexalith.Folders/Authorization/TenantAccessAuthorizer.cs) exposes Tenant watermark/timestamp but uses age-based freshness rather than a Tenant source-head comparison. [TenantAccessOptions.MutationFreshnessBudget](../../src/Hexalith.Folders/Authorization/TenantAccessOptions.cs) defaults to five minutes, which does not establish the annex's two-second resolution authority boundary. [LayeredFolderAuthorizationService](../../src/Hexalith.Folders/Authorization/LayeredFolderAuthorizationService.cs) selects a Folder watermark in place of the Tenant watermark. One watermark cannot certify the complete permission decision.
- [LayeredFolderAuthorizationDecisionSnapshot.DecidedAt](../../src/Hexalith.Folders/Authorization/LayeredFolderAuthorizationDecisionSnapshot.cs) is a policy decision time. `EffectivePermissionsFreshness.ObservedAt` is captured before awaited projection/head reads; neither is a demonstrated File provider verification instant. No validity window or expiry guarantee was found.

Keep optional v1 evidence as the preferred design, conditional on a preserved scoped native revision tuple, truthful timestamps, currentness/recheck semantics and compatibility proof. Do not populate guessed versions or add expiry. The existing positional constructor, deconstruction and numeric Outcome representation must survive. Verify old reader/new payload, new reader/old payload, absent/null evidence and exclusion of usable evidence for stale/unavailable results. Use an additive version if compatibility fails. No v1 evidence property or alternative version is shipped, and no compatibility pass is claimed here.

# Whole-architecture rubric review

**November 20, 2026 · Verdict: changes required.** Three high-severity inconsistencies could cause independent clients or consumers to implement incompatible contracts. Two medium findings affect authority and deployment choices. This review covers the canonical initiative-level architecture record, including the integration and implementation guidance after its decision tables.

## High

1. **The canonical journey sends every client to an EventStore command URL.** The integration description at architecture lines 1632 and 1648–1654 directs SDK, direct REST, CLI and MCP clients to `POST /api/v1/commands`. An SDK team following that diagram would skip the Folders REST operation, including its request schema and authorization boundary. The Folders v1 OpenAPI declares `/api/v1/folders` at line 156. The v2 OpenAPI declares `/api/v2/folders` and `CreateFolder` at lines 154–158. A-11 and A-12 at architecture lines 669–670 distinguish recorded routing control and Gateway enrollment. **Remedy:** draw the Folders REST and generated SDK path to the version-selected operation. Show the McpCli heads as a separate Gateway path for eligible operations. Label internal command envelopes and callbacks separately.
2. **The prescribed Dapr topics differ from the producer and subscriptions.** Architecture lines 923–924, 1634–1635 and 1659 use tenant-prefixed Folders and Tenants topics. Configuring a subscriber from that text would leave the shipped producer's events undelivered to it. Production topic scopes name `folders.events`, `tenants.events` and `memories-events`; tenant isolation remains the responsibility of envelope and partition checks. See `deploy/dapr/production/pubsub.yaml` lines 12–21, `FoldersSemanticIndexingDefaults.cs` lines 16–20 and `FoldersTenantEventSubscription.cs` line 11. **Remedy:** use the deployed topic names consistently in constraints, examples and diagrams. Distinguish the broker component and subscription scopes from the managed tenant in the event.
3. **The lock error example violates the wire contract it illustrates.** Architecture lines 897–914 show a 409 response, uppercase code, `wait_and_retry` and extra lock details, and omit the required visibility field. For AddFile, the v2 OpenAPI at lines 6743–6754 gives HTTP 423, category `lock_conflict`, code `workspace_locked`, action `retry`, and only `visibility` plus `lockStatus` in the example details. The architecture’s A-8 requires `details.visibility` at line 666. Copying the example would produce a different error identity and expose metadata beyond that contract. **Remedy:** reference or reproduce the operation-specific OpenAPI example, including its approved detail keys, and identify its API version.

## Medium

4. **New exceptions have competing approval instructions.** Architecture line 194 assigns new decisions to Jerome. Lines 633 and 653 still instruct Product, Architecture and Security to amend confidential-value policy, or Security and Architecture to approve individual endpoint exceptions. The governance policy assigns material project decisions to Jerome and retains the historical role signatures as provenance. See `docs/governance/approval-policy.md` lines 3, 13 and 19. **Remedy:** identify Jerome as decision owner for a material project exception, and distinguish the relevant security, legal, platform and deployment evidence owners and environment controls.
5. **The production broker fallback exceeds the named supported profile.** D-5 at architecture line 607 describes RabbitMQ or Azure Service Bus as escalation choices once throughput or durability requires one. I-10 at line 744 and the co-normative supported profile require a separate durable, replicated Redis Streams-compatible broker. See `docs/deployment/supported-mvp-profile.md` lines 17–22 and 35–37. Two deployment teams could choose different brokers and claim qualification against the same profile. **Remedy:** bind D-5 to the named broker for this profile and put a different broker behind a profile change and new qualification.

## Coverage and release posture

The updated delivery posture identifies owners and observable outcomes for provider intent and reconciliation, durable indexing retries, metadata-only audit and observed health. It records package publication, planning approval, individual execution authority and deployment acceptance independently. The unresolved Git provider fixture, deployed 1.17 intake, production readers and regional recovery drill are disclosed evidence gaps. Closing them requires their respective runtime and owner evidence. This rubric does not count them as additional documentation findings.

The architecture covers authority and tenancy, state mutation, client and provider boundaries, operational profiles, recovery and deferred product scope. The five findings concern rules that an implementer can follow today and still produce an incompatible configuration, output or decision path. No change to the architecture, technical controls, story state or release posture was made during this review.

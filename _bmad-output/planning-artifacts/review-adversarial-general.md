## Verdict

The triage fixed what it was told to fix and, in doing so, introduced the defects this pass is about: it aligned the PRD's wording to artifacts it did not read to the end. The completion rows now cite "the approved C6 matrix," but that matrix (architecture, mapping, and the 1:1 `FolderStateTransitions.cs`) contains no transition by which a `dirty` workspace is ever re-locked, continued, committed, or released by the originating task, sends a known commit failure to `failed` rather than `dirty`/`locked`, and returns `inaccessible` to `ready` rather than to `dirty` — so the "only MVP exit" of UJ3 is `state_transition_invalid` under the artifact the PRD calls approved, and the C6 row admits only two of the six disagreements. The safe-denial invariant was restated as per-operation indistinguishability "in status," yet 46 of the 49 Spine operations declare both a 403 and a 404 safe denial with the same category and code, and PD10 does not record that as a defect. The level-based permission table makes UJ1 impossible for a tenant member without a grant the journey never mentions and hands every audit reviewer and operator a folder `read` that carries file-body reads. Row 3 puts a lease lapse with zero mutations into `dirty`, which by the definition two sections later requires mutations, and which then blocks archive forever, exempts the workspace from cleanup, and counts as recovery burden. `failed` is task-terminal and cleanup-eligible, so a non-retryable commit failure discards staged work after seven days while the document still says "No MVP operation discards staged changes." None of these is a governance gap; each is a sentence that a story-writer will implement wrongly or refuse to implement. The document is not yet fit to be the release-gate reference it claims to be; it is fit for a third, narrow pass.

## Findings

The translated matrix contains, from `dirty`, exactly two transitions: `ReconciliationRequested → reconciliation_required` and `OperatorDiscardRequested → failed`. Do not leave both texts labelled approved.

That is precisely the "status" difference the invariant forbids per operation, and it discloses "you exist but are denied" versus "this may not exist" on every protected surface. PD10 records three leaking enum members on ten operations, the missing `details.visibility` requirement, the missing mapping, the release-reason enum, and the permission representation; it does not record the dual-status declaration, which is the widest conformance defect in the Spine. Second, the safe-denial category is still not spelled: the product-owned exception list names `category`, `code`, `idempotency_key_expired`, `isTruncated`, and the header, but not the value that carries the enumeration property, and "the `SafeAuthorizationDenial` envelopes" are response names, not a category. Under the Actors table every negative case ("wrong-tenant, revoked, stale, disabled, unknown, hidden-resource caller") "fails closed with the safe denial," and §Authentication says disabled/deleted/stale/revoked authority "fails closed," so there is no residual population for a distinguishable "tenant authorization denied"; the family is either dead or a leak, and the mapping rule "every Spine category maps to exactly one family" cannot assign `tenant_access_denied` to both. *Fix:* Spell the safe-denial category and code in the exception list; state per operation whether the safe denial is 403 or 404 (one rule, e.g. "404 on every resource-addressed operation, 403 only on tenant-level operations with no resource in the path") and add "dual 403/404 safe denials on 46 operations" to PD10 with the same owner and date; delete "tenant authorization denied" from FR44 or define the one caller class that receives it distinguishably and why that is not enumeration.

- **[high]** Row 3 puts a mutation-free workspace into `dirty`, contradicting the definition of `dirty`, and the consequences are permanent (§Task and Lock Completion Model row 3 "Lease lapses before any staged change → `dirty` / `expired`, then `stale` ... any other task is denied"; §Workspace State "`dirty` means mutations are present and the lock lapsed, was revoked, or a commit failed"; "`changes_staged` means known mutations are applied under a valid lock with no interruption"; FR13 "no `changes_staged`, `dirty`, ... workspace"; FR30 "Dirty ... workspaces are not cleanup-eligible"; CM2; UJ3 "its workspace lifecycle is `dirty` ... its lock state is `locked` until the lease lapses") — A task that acquires a lock, writes nothing, and dies now leaves a `dirty` workspace that only it can release. Because only the originating task may act, and it will never return, the folder can never satisfy FR13's archive precondition, the temporary working copy is never cleaned (FR30 excludes `dirty`), and CM2 counts the task as recovery burden even though nothing needs recovering. The previous review's "stale lock on a clean workspace blocks archive" was fixed by making it worse: the clean workspace is now also uncleanable and metric-visible. Separately, the `changes_staged` definition depends on "no interruption," which the server cannot observe while the lease is valid; UJ3 then asserts the interrupted workspace is `dirty` while its lock is still `locked`, which the definitions make impossible (`dirty` requires a lapsed/revoked lock or a failed commit; a valid lock with mutations is `changes_staged`). Finally, after a row 5 or row 6 re-acquisition the workspace holds a valid lock but stays `dirty`; whether the next mutation moves it to `changes_staged`, and whether FR37's "commit a valid locked workspace" accepts `dirty`+`locked`, is unstated and, per the first finding, untransitioned. *Fix:* Row 3 → `ready`/`expired` (a lapse with no mutations returns the workspace to its pre-lock content; any authorized task may lock it), or keep `dirty` and add a platform-owned no-change release at the C7 stale threshold. Delete "no interruption" from the `changes_staged` definition; make UJ3's interruption observable (lease lapse) or say the lifecycle is `changes_staged` until it lapses. Add one row: "Originating task re-acquires in `dirty` → `changes_staged`/`locked`."

- **[high]** `failed` and `inaccessible` are task-terminal and cleanup-eligible, so the no-discard rule is broken by FR30 (Glossary "Task-terminal: The current task has ended in `committed`, `failed`, `inaccessible`, or explicit no-change closure ... Failed/inaccessible closure ... provides the same C3 seven-day observation window before cleanup"; FR30 "deletes temporary working files at the C3 seven-day boundary"; row 10 "Known non-retryable provider failure (`failed`) ... Mutations, commit, release, and takeover are denied"; row 6/A18 "the workspace returns to `dirty` with its changes intact"; UJ3 "No MVP operation discards staged changes"; PD2(b) "keep the no-discard rule"; C6 matrix `changes_staged + CommitFailed → failed`) — Under the approved matrix every known commit failure is `failed`; under the PRD a "non-retryable" one is. `failed` is task-terminal, so seven days later FR30 deletes the working copy holding Asha's staged changes. That is a discard, performed by the platform, of exactly the work UJ3 promises to preserve; and UJ5's scenario (credential lost push permission, provider 403) is the likeliest producer. The document gives no rule for sorting a provider failure into row 8 (retryable, work kept, lock kept), row 10 (non-retryable, work deleted after seven days), or row 6 (authorization failure, work kept and resumable); the same provider 403 fits all three. `inaccessible` has the same defect in the other direction: the Glossary makes it task-terminal with a seven-day window, A18 makes it resumable "with its changes intact," and nothing says "intact for seven days." Worse, the context-read rule lists `ready`, `locked`, `committed` for any reader and the four owner-only states; `failed` and `inaccessible` are absent, so no actor, not even the owner, may inspect the staged changes before cleanup deletes them. *Fix:* Decide: either `failed` with staged changes is not cleanup-eligible (add it to FR30's exclusion list and to FR13's precondition), or the completion model states that a non-retryable commit failure discards after seven days and UJ3/PD2 drop "no discard." Define the classification: retryable = provider transient/rate-limit/timeout; non-retryable = policy rejection with the change set intact (branch protection, invalid ref); authorization = any 401/403/credential result → `inaccessible`. Add `failed` and `inaccessible` to the owner-readable set or say why not. Make `inaccessible` non-task-terminal while A18 stands.

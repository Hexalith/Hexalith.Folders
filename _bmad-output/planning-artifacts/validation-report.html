high

Clean-workspace reads specify two different grants

§ Endpoint Specifications and Protected operation families; PRD lines 467–475, 586–592
The endpoint paragraph says a ready, locked or committed workspace is readable by “any actor holding the folder read grant” and includes body search and range reads. The permission table and A22 require write for the context-read family. An audit reviewer with only folder read could receive file contents under the first interpretation.
Suggested edit. Specify the grant per operation before applying workspace-state and task restrictions. Use a read-only principal and a write-authorized principal on the same clean workspace to distinguish allowed status inspection from protected content reads. Authorization matrix, context-read family and operation inventory

A protected ACL denial has two caller-visible expectations

§ Error Codes and FR44; PRD lines 630–636, 949–950
FR44 requires callers to distinguish “folder ACL denied,” while the v2 rule maps insufficient folder scope to the same 404 as a missing or hidden resource. A distinct response could disclose whether a protected folder exists.
Suggested edit. Map the ACL-specific reason to bounded audit evidence and specify a single public 404 for fresh negative facts. Preserve the separate 503 for unusable authority evidence. Reconcile any change to FR44 with the mirrored epic wording and C13 mapping. Authorization matrix, canonical outcomes
high

An interrupted local file mutation has two recovery paths

§ Command and Query Contract, Error Codes and Glossary; PRD lines 511, 536–551, 640, 874
The command contract assigns an interrupted local file batch to dirty with per-operation evidence because it has no provider side effect. The error section says an unconfirmed “file mutation” enters unknown_provider_outcome, and the glossary includes it as an external effect. The two paths entail different locks, evidence and retry instructions.
Suggested edit. Classify by the side effect that may have occurred. Specify local operation recovery for staged file bytes and reserve bounded provider reconciliation for uncertain external writes. Check both cases before allowing commit. OQ8 admission state machine
high

Confirmed commit refusal lacks its terminal branch

§ Task and Lock Completion Model; PRD lines 529–540, 750
The reconciliation instruction says “confirmation of no remote update transitions to dirty” and permits another lock and retry. A confirmed upstream refusal also leaves the ref unchanged. C6 sends that refusal from an unknown outcome to failed, while a known retryable failure with no remote effect preserves staged changes in dirty.
Suggested edit. Distinguish affirmative refusal, positively verified retryable non-application, confirmed success and unresolved evidence. Name the allowed state and next action for each. C6 guard discriminators
medium

The release test lists only half the negative authorization states

§ Actors and Contract and Quality Gates; PRD lines 570, 706, 1118
The quality gate explicitly lists four negative cases. The September matrix contains eight, adding disabled, unknown, absent-resource and insufficient-scope to that list. A team could satisfy the checklist while missing these four independent inputs.
Suggested edit. Derive the test population from all eight matrix rows and check the expected 404 or 503 and zero protected observations for each. Authorization matrix, Canonical Negative Access States
medium

The equivalence rule omits behavior-affecting credential scope

§ Command and Query Contract; PRD lines 544–550, 944–945
The list introduced by “equivalent intent means” includes delegated task scope and excludes authentication tokens. The governing idempotency rules also compare server-derived credential scope when it changes behavior. Without that distinction the acceptance text can classify a different intent as an equivalent replay.
Suggested edit. Include the behavior-affecting scope in the comparison and keep raw token bytes excluded. Cover unchanged scope with a refreshed token and changed scope with the same live key. Idempotency and adapter parity rules, admission identity

Downstream usability

thin

The stable IDs, glossary and named journeys make individual sections easy to cite. Several journeys still describe a broader permission or a different recovery decision than the table used by the contract and operator console.

high

Restarting the caller can imply a second valid lock

§ UJ3, Task identity and Workspace State and Concurrency; PRD lines 289–293, 515, 523–525, 658
Asha's process stops with staged work and a still-valid lock. The journey immediately calls the workspace dirty and offers a “new lock instance.” The lock rule returns the existing instance and ownership proof while the lease is valid. Lease expiry is the documented transition from staged to dirty in this case.
Suggested edit. Walk the same task through restart before expiry and after expiry. Give each case its observed workspace state, fence and legal acquisition behavior. Architecture, C6 transition matrix
medium

Dirty workspaces do not all require a person

§ Workspace State and Concurrency; PRD lines 652–658, 924
The state summary labels all dirty workspaces “awaiting-human” and says no automatic transition will occur. The adjacent clean/stale rule returns a workspace to ready automatically. C6 also distinguishes work the originating task can resume from orphaned staging.
Suggested edit. Have status and console acceptance use the C6 disposition for clean, resumable and orphaned cases. C6 state catalog
medium

Operator diagnostics and readiness validation require different permissions

§ UJ2, Protected operation families and FR15; PRD lines 279–285, 581, 594, 905
“A platform engineer acting as a tenant-scoped operator may validate” can be read as permission to invoke the readiness validation operation. That operation requires tenant folder-create authority. An operator can inspect provider support evidence under a different permission.
Suggested edit. Give the journey two named actions and explicitly identify the additional grant when the operator performs validation. Authorization matrix, PD10 amendment and readiness family
medium

The administrator journey implies effective-permission lookup for another actor

§ UJ9 and FR5–FR6; PRD lines 351–353, 587, 889–890, 1179
Elise asks “Who can write here today?” and checks the automation team's grant in the effective-permissions view. PD10 restricts that operation to self-inspection. An administrator can list ACL entries, but those entries alone do not establish another principal's effective access after membership and delegation checks.
Suggested edit. Use the administrator's ACL-list operation to confirm the granted entry, followed by the intended principal's self-inspection to confirm effective access. Authorization matrix, PD10 amendment

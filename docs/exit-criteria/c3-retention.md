## Decision

The September 15 authority changes only the temporary-working-files cleanup trigger: the full seven-day
destructive-retention window starts after terminal task closure with no active task. Architecture additionally
uses a separate non-destructive recovery clock for the guarded `inaccessible` transition; that clock is not a
C3 deletion deadline. The candidate policy cannot serve as release approval until A7b is signed.

For staged content, first inaccessibility sets `stagedRecoveryStartedAt` and `stagedRecoveryDeadline`; those
fields only bound automatic return to `dirty`. A qualifying terminal/no-active epoch separately sets
`stagedCleanupStartedAt` and `stagedCleanupNotBefore` exactly seven calendar days later. A legitimate resume
cancels that cleanup epoch, and a later terminal/no-active closure starts a fresh P7D epoch. Lock expiry, lease
staleness, cancellation alone, retry, restart, recovery-deadline expiry, and an `inaccessible` transition never
delete content. Cleanup requires the cleanup deadline elapsed, the task still terminal, no active task, and no
legal hold. The lifecycle matrix changes state only and never performs cleanup.

## Rationale

C3 is Phase-1-blocking because the Contract Spine must expose D-7 idempotency TTL semantics before client and parity work starts. The proposed durations keep audit and reconciliation evidence long enough to support operational review while keeping temporary working files short-lived because they are disposable caches, not authoritative state.

No unaffected row changes its recorded approval. The temporary-working-files row is a candidate fixed by the approved September 15 proposal and is explicitly blocked on A7b rather than inheriting the superseded digest.

The table covers eleven data classes: the six explicitly enumerated by the Phase 0.5 workshop scope (audit metadata, workspace status, provider correlation IDs, read-model views, temporary working files, cleanup records), four additional classes the workshop classified as separate retention concerns (folder metadata and soft-delete markers, auth claims copied into metadata, diagnostics and rejected-command records, and commit idempotency records), and the independently governed OQ8 consumed-key evidence class. The consumed-key row is required and cannot be inferred from either replay-result tier.

## Verification impact

Verification must prove this artifact exists, contains no generic placeholders, contains only metadata-only examples, and maps each duration to a consuming future story or artifact. OQ8 verification additionally proves tenant-partitioned protected key digests, result/intent compaction, exact boundary behavior, digest-key rotation, fail-closed collision/corruption handling, legal-hold pause/resume, final tenant deletion, and persisted tombstone end state without exposing raw keys or digests.
